# Media upload release 426

## Upload optimization

Runtime config version `2026-09-13.6` adds independent encoding/chunk kill switches and a stable, build-gated upload experiment. Only build 426 or later can enter the 10% adaptive cohort; other clients retain baseline behavior. Both client switches default off when absent. Changing the encoding switch invalidates cached local preparation decisions. The prior playback experiment remains independently controlled.

Upload throughput history uses accepted PATCH bytes and request elapsed time, separated by network class from playback/download measurements. It expires after six hours, requires two measurements, and uses a conservative estimate. Measurements spanning a detected network-class change do not train the predictor. Upload result events include resident memory, Low Power Mode and thermal state; resident samples are not peak memory or battery-drain measurements.

Adaptive encoding applies to unusually large, slow-to-transfer, explicitly Rec.709 sources at up to 1080p and 24–30 fps. HDR, wide-gamut/unknown-color, 4K, and higher-frame-rate sources retain their existing path. Efficient sources remain untouched. The actual Apple HEVC 1080p exporter retains the existing 8.2 Mbps target; there is no additional 720p quality fallback. Export attempts have a 12-second timeout and propagate cancellation. Candidate codec/container/fast-start, presentation dimensions, frame rate, audio presence, duration and color metadata are validated. Four matched presentation frames are color-managed to sRGB and compared with RGB block SSIM and absolute color error; every sampled frame must meet both thresholds. This sampling is a conservative guard, not a perceptual guarantee for every frame. A candidate must save at least 25% of bytes and its predicted transfer savings must exceed measured export/inspection/quality-check cost by at least 50%. Rejected/failed candidates are deleted, and the unchanged source follows the existing path.

Adaptive TUS chunks start at 5 MiB, target about eight seconds using accepted request timing, grow at most twofold, and shrink on failure. Provider bounds and 256 KiB alignment remain enforced, except for the final remainder. Constrained paths stay at 5 MiB; other limited paths cap at 20 MiB, and standard paths retain the configured ceiling. The same controller spans the foreground retry loop and background delegate chain. Requests remain sequential, acknowledged offsets remain exact, and retry/relaunch recovery still checks HEAD before sending more bytes. Baseline chunk sizes remain unchanged.

## Recovery and finalization

Manual retry checks active ownership before resetting queue state. Recovery is coalesced and excludes active IDs. Connection interruptions become paused uploads with persisted, bounded backoff; rejected uploads remain failed. Existing reconnect/app-active recovery is retained. Foreground automatic recovery emits a persisted completion notification so the normal story registration/readiness flow updates immediately. Progress persistence is throttled to one second during ordinary upload callbacks, while state changes, retries and prepared sessions remain durable. An ETA is shown only when a measured estimate is available, and it disappears during finalization.

Backend tracing now correlates total completion, authentication, rate limiting, claims, duplicate lookup, provider work, creator/element validation, asset/story database work, moderation, response reads, claim persistence and claim release. Trace failures cannot change the completion result. Independent owner-bound response status/overlay reads now overlap. Authentication, ownership, idempotency, moderation, publication and provider-error persistence rules remain intact.

The admin media dashboard groups upload outcomes/timing by build, connection, device model, upload experiment and file-size range. Small cohorts are explicitly preliminary; effective Mbps excludes retry attempts, and overlapping snapshots are not independent evidence. The production comparison SQL was validated read-only against the real database. No new database migration, hosting migration, or separate Cloudflare deployment is required.

## Quality and device verification

`media-upload-quality-audit-426.json` records synthetic motion, dark scenes, detail and skin-color-palette fixtures using the actual Apple exporter. Audio, frame rate and Rec.709 metadata were preserved. A known degraded noise/detail export was separately rejected by the matched-frame guard. An end-to-end preparation test accepted a validated candidate with synthetic container padding and verified that the source checksum was unchanged; this proves branch behavior, not real-world savings for typical camera footage.

Physical-device acceptance remains necessary for real skin tones, high-motion footage, dark scenes, HDR playback tone mapping, OS suspension and energy use. Existing Cloudflare Stream playback converts HDR to SDR; this release deliberately does not add another client HDR conversion. See [Cloudflare Stream FAQ](https://developers.cloudflare.com/stream/faq/).

Device matrix for TestFlight: Wi-Fi/cellular/constrained connections; efficient and unusually large camera/library videos; 10-item batches; lock during transfer; disconnect/reconnect mid-PATCH; resume after relaunch; expired upload leases; duplicate finalization; verify no missing or duplicate stories and check original/audio/orientation/color against playback. A user force-quit may stop iOS background work until the app is opened again. Compare matched baseline/canary cohorts with adequate independent samples before expanding rollout. Instruments energy and memory profiles are required to establish battery drain and peak memory; simulator transport tests do not establish those results.
