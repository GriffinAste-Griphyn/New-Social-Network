# Media upload release 433

## Production incident and recovery

Build 432's latest 21,186,978-byte upload measured 18,432 ms of transfer and 20,603 ms from Post to server acceptance. Provider readiness was first recorded approximately 34 seconds after Post. Publication remained pending because the new moderation update returned a text CASE expression for a PostgreSQL story_status enum column. Production workflow logs showed repeated failed writes and status polling repeatedly starting recovery workflows.

Release 433 casts the atomic publication expression to story_status, preserving the current-row readiness, scan, deletion, expiration and worker-token fences. PostgreSQL EXPLAIN reproduced the original enum mismatch and accepted the corrected expression without executing any update. Regression coverage checks the actual generated SQL.

An initial server hotfix, dpl_2joqoaB7dLdsMRmfY1PPxBsb1uW5, reached production READY. ## Changes

- A database dispatch claim coalesces moderation requests before creating workflow runs or after-response work. It retains successful dispatches for 30 seconds, excludes active worker leases and ineligible/deleted/expired stories, avoids dispatching unprepared images, and releases failed dispatches with a token fence. The existing reconciliation cron reaps expired dispatch and worker claims. Existing worker result fencing remains intact.
- Private early video upload defaults on for unmetered paths when no saved preference exists. Explicit opt-outs are preserved, and the composer continues to show Start upload early with its private/Wi-Fi explanation. Network-budget changes retry eligible speculative work; failed private attempts release their composer entry so a later eligible path can restart.
- Posting during an unfinished private transfer durably stages the exact prepared source and UUID, then transfers ownership to the pending queue without awaiting network completion in the composer. Dismissal cannot cancel adopted work. The pending queue awaits the existing transfer before taking the global video-transfer permit, avoiding a permit deadlock. Progress callbacks move to the pending item. Completed receipts are checked against account, origin, UUID, file fingerprint and checksum and persisted before skipping any transfer.
- Failed adopted transfers retain the durable source and UUID for normal resumable upload recovery. Account changes cannot fall through into a transfer for a different account. Failed manifest writes do not take speculative-transfer ownership. Process restart retains the staged source and upload UUID even if the transient handoff task no longer exists.
- Optional SDR-only HEVC preparation uses a 6 Mbps candidate budget while mandatory normalization retains its 8.2 Mbps budget. A candidate is accepted only when the existing visual, color, dimensions, frame cadence, duration, audio-presence, byte-savings and estimated total-time checks pass. HDR, unknown color, 4K and high-frame-rate inputs retain their established path. Build 433 supports this quality-gated path outside the old upload canary cohort; the existing production encoding flag enables it and remains a rollback. Older supported canary clients retain their existing encoder and cohort checks.
- The existing Vercel HLS pipeline can repackage compatible H.264 frames instead of encoding a matching rendition again. Eligibility requires exact target geometry, square pixels, explicit Rec.709, 8-bit 4:2:0, known High/4.1 AVC, bounded bitrate and supported cadence. Every SPS is checked for progressive compatible AVC headers, every segment's first video packet must be IDR, segment durations are bounded, and package geometry/cadence/duration are verified. Unsupported or failed repackaging uses the normal encoder. The planner prioritizes a reusable source rendition before encoding additional profiles. Original files, separate verified audio, signed/private delivery, publication approval and enhancement work remain intact. Encoder version advances to v8 to separate cached renditions.
- Cloudflare can publish before its all-quality-levels percentage reaches 100 only after a source-appropriate AVC/AAC rendition is advertised, complete video and separately advertised audio playlists are available, and initialization/first media resources return successful HEAD responses. Verification is bounded to 64 KiB per playlist and 1.5 seconds, follows no cross-origin references or redirects, and fails closed to normal full readiness. Proof is retained through concurrent provider observation merges, checked against source dimensions and separated from the full-quality diagnostic. Provider errors, removed stories, scan checks and approval still prevent publication. MEDIA_VERIFIED_PLAYBACK_PUBLICATION_ENABLED=false rolls this path back; MEDIA_SOURCE_REPACKAGING_ENABLED=false rolls source reuse back.

## Limits

The source-reuse path applies to the existing Vercel HLS processor; it does not control Cloudflare's internal encoders or migrate the live Cloudflare upload route. Verified Cloudflare readiness can save a wait only when the required rendition is ready ahead of the 100% marker. Private early transfer overlaps editing only on permitted unmetered paths. Physical-device upload bandwidth and Apple build processing remain external constraints. No new hosting service, queue, worker capacity or database migration is introduced, and no measured production speedup is claimed from fixture tests.
